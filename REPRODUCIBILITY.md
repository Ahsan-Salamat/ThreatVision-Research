# Reproducibility

## Safe research tests

Use Python 3.11 in a virtual environment. From the repository root:

```bash
python3 -m pip install -r requirements-research.txt
python3 -m unittest discover -s tests -v
python3 -m compileall -q research tests
```

The safe suite uses generated byte fixtures and synthetic predictions. It does not need malware files, private datasets or model weights. The verified local run used Python 3.11.15, TensorFlow 2.16.1, Keras 3.14.1 and NumPy 1.26.4; the latest result was 38 passed. Model-dependent tests are not part of this safe suite.

## Verify a checkpoint

The checkpoint files are not distributed here. Install the model runtime recorded in [`requirements-model.txt`](requirements-model.txt), then run the verifier with the exact model bytes and the matching registered profile. The verifier checks SHA-256 before safe deserialization and rejects an unregistered identity.

```bash
KERAS_BACKEND=tensorflow python3 -m research.verify_model \
  "/path/to/threatvision_v01.keras" \
  --sha256 1e8f713db5aa0e42bb55addb02281a700028fc9fbca784b908c77a1b9cf6aaca \
  --profile production-224-v1 \
  --output /tmp/production-checkpoint-verification.json
```

For the separate recovered `best_model.keras`, use profile `recovered-256-v1` and SHA-256 `62feb539c30edb4b2849ac760d9b9e41c8842da000e9bfc9c653b08861173102`. Do not interchange the files or profiles. Each check runs five deterministic synthetic inputs and one harmless PE-derived probe and verifies finite, in-range, repeatable output. This is runtime verification, not classification evaluation. The checked outputs are recorded in [`docs/audits/production-checkpoint-verification.json`](docs/audits/production-checkpoint-verification.json) and [`docs/audits/recovered-256-checkpoint-verification.json`](docs/audits/recovered-256-checkpoint-verification.json).

## Repeat preprocessing parity

The recorded parity run compared the research pipeline with the companion application's converter on three deterministic harmless fixtures. The application source is external to this repository, so rerunning this comparison requires that local checkout. Supply the converter and actual production model:

```bash
KERAS_BACKEND=tensorflow python3 -m research.preprocessing_parity \
  --converter "/path/to/ThreatVision Final/backend/python_scripts/convert_to_bigram_dct.py" \
  --checkpoint "/path/to/threatvision_v01.keras" \
  --checkpoint-sha256 1e8f713db5aa0e42bb55addb02281a700028fc9fbca784b908c77a1b9cf6aaca \
  --output /tmp/production-preprocessing-parity.json
```

The record establishes current serving-code parity, not historical training parity. See the [method and results](docs/audits/PRODUCTION_PREPROCESSING_PARITY.md).

## Data-dependent workflows

Manifest validation requires real, authorized PE files, complete metadata, unique hashes and independently supported labels. For a proposed cohort, validate it before extracting features:

```bash
python3 -m research.validate /data/manifest.csv /data/pe-files
```

Feature extraction additionally requires the production static-analysis source and the exact 224×224 model; its output sidecar records source, manifest, preprocessing and checkpoint hashes. Split generation and evaluation require those genuine per-sample features and labels. They must not be run with synthetic pseudo-labels as scientific evidence.

The training script initializes fresh weights from an architecture topology. It does not reproduce historical training. Its `--smoke --cpu` option is only for pipeline wiring and requires a temporary manifest; any pseudo-labels must be explicitly marked as non-ground-truth. The smoke scores are not research results. See the [experiment lineage register](docs/experiment-lineage.md) for historical records and the [model card](docs/model-card.md) for model-specific limits.
